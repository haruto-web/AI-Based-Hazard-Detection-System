ENHANCED SECURITY FEATURES
===============================================================================

1. 🔐 ROLE MODIFICATION PREVENTION
   --------------------------------
   Users CANNOT change their own role field:
   
   BAD REQUEST (now blocked):
   {
     uid: "user123",
     action: "update",
     data: { role: "HSE Head - Head Office" }  ← DENIED!
   }
   
   The roleNotChanged() function prevents privilege escalation attacks.

2. 🔐 AUDIT LOGGING WITH SHA-256
   ------------------------------
   All security events logged with tamper-proof signatures:
   
   Log Entry Structure:
   {
     userId: "user123",
     action: "USER_LOGIN",
     timestamp: "2026-06-10T12:00:00Z",
     signature: "a7f8d9e2..." ← SHA-256 hash of entire entry
   }
   
   If someone modifies the log, signature won't match = detected tampering!

3. 🔐 GRANULAR PERMISSIONS
   -----------------------
   Different roles have different access:
   
   Site Project Engineer:
   ✅ Can view dashboard
   ✅ Can view streams
   ❌ Cannot access reports
   
   HSE Head - Head Office:
   ✅ Full dashboard access
   ✅ Full streams access
   ✅ Can generate reports
   ✅ Can manage sites
   ✅ Can view audit logs
   ✅ Can delete users

4. 🔐 READ-ONLY AUDIT TRAIL
   -------------------------
   Reports and audit logs CANNOT be modified or deleted:
   
   allow update, delete: if false;
   
   Once created, they're permanent = integrity guaranteed!

EXAMPLE 1: Log user actions with SHA-256 integrity

import { logUserLogin, logDataModification } from './utils/auditLogger';

// After successful login
await logUserLogin(user.uid, user.email);

// When user modifies data
await logDataModification(user.uid, 'sites', siteId, 'update');

EXAMPLE 2: Verify data hasn't been tampered
--------------------------------------------
import { verifyDataSignature } from './utils/security';

const logEntry = await getDoc(doc(db, 'audit_logs', logId));
const isValid = await verifyDataSignature(
  { userId: logEntry.userId, action: logEntry.action, timestamp: logEntry.timestamp },
  logEntry.signature
);

if (!isValid) {
  alert('⚠️ Log has been tampered with!');
}

EXAMPLE 3: Check user permissions before UI actions
----------------------------------------------------
import { hasFullAccess } from '../config/roles';

if (hasFullAccess(userRole, 'reports')) {

  // Hide button - user doesn't have permission
}

QUESTIONS & ANSWERS
===============================================================================

Q: Will this break my existing app?
A: No. The rules are backward compatible. Your current users/sites
   collections work exactly as before. New features are additions only.

Q: Do I need to update my frontend code?
A: The enhanced security utilities are optional. Your app will work
   without them, but using them adds extra protection (audit logging,
   input sanitization, etc.)

Q: What happens to existing data?
A: Nothing changes. All existing data remains intact. The new rules
   just control HOW users can access that data going forward.

Q: Can users still register and login?
A: Yes, exactly as before. The authentication flow is unchanged,
   just enhanced with audit logging and password strength checking.

Q: How do I view audit logs?
A: Only users with Head Office roles can view audit_logs collection
   in Firestore Console. You can also build a UI for this.

Q: What if I need to change someone's role?
A: Currently, roles can only be changed through Firebase Console
   directly. In the future, you can add an admin panel for this.
